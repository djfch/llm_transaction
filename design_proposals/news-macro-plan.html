1

为什么 v1 不行、v2/v3/v4 怎么改

v1 的问题

把新闻当"决策输入"喂给执行 agent：时效性追不上（市场秒级反应 vs 管道分钟级）、LLM 因果解读不可验证、近因偏差会绑架仓位判断、全量建设却无验证设计。

v2/v3 的核心改变

新闻/宏观只进研报 agent，不进执行 agent。研报 agent 定时产出结构化方向结论，执行 agent 只读结论 + 遵守代码级方向约束。v3 能力放开（30 次工具、token 不限、全量新闻、时间线+判断史）。

v4 的闭环强化

复盘 agent 接入对照与纠错：对照研报判断 vs 实际走势，三层纠错，并可带证据版本化修订研报提示词——三段闭环从"信息流"变成"自我进化系统"。

3

研报 agent 设计

原则：能力放开（质量优先）、两端结构化（输入代码决定、输出强制 JSON）、护栏只防失控不防能力。

角色边界与护栏

  • 独立 LLM 循环，模式复用 review agent 先例（项目已有只读 agent）
  • 只读工具（9 个，全部进统一审计）

    fetch_calendar — 经济日历（金十 MCP）：今日+明日高星事件（star≥3），带 actual/consensus/previous（实际/预期/前值）

    fetch_flash(hours=24) — 全量快讯（金十+律动 MCP）：以"时间+标题+摘要"紧凑格式返回，一条不丢

    fetch_indicators — 指标快照（律动 MCP）：DXY(美元指数)/美债收益率/M2/ETF 净流入/稳定币市值/情绪值/OI/Bitfinex 杠杆多头

    get_macro_series(indicator, look_back) — 宏观历史序列（FRED，免费 key）：cpi/pce/联邦基金利率/10Y 美债/M2/美元指数等，Markdown 表格（最新值+窗口变化）——补"历史序列"缺口

    get_prediction_markets(topic) — 预测市场概率（Polymarket，公开无 key）："Fed rate cut"/"recession"等事件的市场隐含概率，按成交额排序——比新闻更前置的信号

    fetch_article_detail(id) — 展开单条快讯正文全文（上下文只放标题+摘要，需要细读时按 id 取全文）

    search_news(keyword, days) — 按关键词检索历史快讯/文章，深挖事件的来龙去脉；内部路由：金十/BlockBeats 搜索 API（历史全）+ 本地 timeline 表（补第三方搜不到的事实），两边结果合并去重

    read_timeline(days=7) — 读事件时间线（事实层）：近 7 天世界发生了什么，看跨天因果链

    read_judgments(days=7) — 读历史研报结论（判断层）：近 7 天我怎么看、验证结果、错因——自我纠错输入

  • 写工具（1 个，只写分析笔记，不碰事实与交易）

    submit_causal_links(links) — 提交本次分析得出的链式因果链：有序节点（事件→推断→市场反应→标的结论），节点可挂 timeline_id(事实层引用)，整链带 confidence(置信度)/evidence(依据)/report_id(来源研报)；复盘逐环节验证、定位断点；事实层（timeline 表）100% 代码写入，LLM 零写权限——账本与笔记严格分开

  • 没有任何交易工具，不持有交易所密钥——结构上杜绝"看到新闻就交易"
  • 调度器定时触发（启动时间按第 2 节时间表，提前于开盘/事件时刻），跑完落库即结束，不是常驻服务
  • 护栏：工具调用上限 30 次（防死循环保险丝，非能力限制）+ 单次超时 15 分钟强制终止；token 不限量，只做日志统计，每月复盘一次成本
  • 提示词由外部版本化修订（复盘 agent 带证据修订），自身无权修改自己的提示词

注：事件研究工具（event_study：历史同类事件 × 行情统计，回答"上次非农后 BTC 怎么走"）暂缓实现——待研报框架运行稳定后按需加入；当前历史检索能力由 search_news 承担。

输入（代码决定，不裁剪）

  • 24h 快讯全量：金十 + BlockBeats，以"时间+标题+摘要"紧凑格式全部进上下文，一条不丢；正文全文按需检索（fetch_article_detail）——上下文窗口有限是物理约束，但过滤权完全交给 agent
  • 日历：今日 + 明日高星事件（star≥3），带 actual/consensus/previous
  • 指标快照：律动 MCP 指标组（DXY、美债收益率、M2、ETF 净流入、稳定币市值、情绪值、OI）——硬数据骨架；FRED 宏观序列与 Polymarket 预测概率为按需工具（带参数，不进预注入）
  • 事件时间线（近 7 天）：事实层，见第 4 节
  • 历史研报结论（近 7 天）：判断层，含验证结果与错因，见第 4 节

注入机制：全部预注入第一轮消息，工具只做补充

以上输入由代码组装进第一轮 user 消息（预注入）——LLM 第一次收到消息时已全部在上下文中，不需要、也不能通过工具调用获取。

第一轮消息组装顺序：

[系统提示词] 角色定义 + 任务要求 + 护栏 + 复盘注入的改进指令（L2） [user 消息] ① 日历段：今日+明日高星事件（star≥3，带实际/预期/前值） ② 指标段：DXY/美债/M2/ETF/稳定币/情绪/OI 快照 ③ 快讯段：24h 全量，时间+标题+摘要紧凑格式（一条不丢） ④ 时间线段：近 7 天事件时间线（事实层） ⑤ 判断史段：近 7 天研报结论+验证结果+错因（判断层） ⑥ 任务指令："基于以上信息，输出当日/近期方向研判 JSON"

工具定位（补充而非获取）： fetch_article_detail / search_news 用于深挖（细读某条全文、按关键词搜历史快讯）； fetch_flash / fetch_calendar / fetch_indicators 用于刷新（注入的是启动时点快照，生成过程中想取更新的数据才调用）； read_timeline / read_judgments 可查更长历史（注入已带 7 天）。

特性：① 第一轮输入大——全量快讯+五段数据，单次 5-10 万 token 起步，成本主要在输入侧； ② 注入的是启动时点快照，生成过程中不自动更新（除非主动调工具刷新）； ③ 受上下文窗口物理上限约束——快讯以紧凑格式全量注入，正文按需展开，这是唯一的技术裁剪点。

4

事件时间线 vs 历史判断史

两者都会提到同一事件，但本质不同——时间线是"发生了什么"（事实），判断史是"我怎么想、想得对不对"（判断）。研报 agent 用时间线理解因果，用判断史自我纠错。

研报 agent 每次产出时，同时更新两份持久记录

事实层 · timeline 表

事件时间线（近 7 天，持续累积）

客观记录：时间 | 事件 | 来源。如：
07-30 油价 +5%（中东局势）｜金十
07-31 美债 10Y 收益率上行 12bp｜指标
08-01 BTC 单日 -3%（放量）｜行情
08-03 非农预期 8.3万 前值 5.7万｜日历

用途：看清跨天因果链——"3 天前油价大涨 → 昨天美债上行 → 今天 BTC 承压"

判断层 · reports 表

历史研报结论（近 7 天）

主观记录：日期 | 方向 | 置信度 | 核心依据 | 验证结果 | 错因。如：
08-01 看空 高 依据：美债上行
→ 实际 +1.2% 错，错因：解读错误（忽略 ETF 流入）
08-02 中性 中 依据：多空交织
→ 实际 -0.8% 中性偏对

用途：自我纠错——连续 5 天看多但 BTC 一直跌，该怀疑自己的判断框架了

不重复的理由：时间线回答"世界发生了什么"，判断史回答"我的判断体系是否可靠"。复盘 agent 对照实盘时，也是用这两份做偏差分析——判断错在哪：是信息不足（时间线缺了关键事件）还是解读错误（信息全但因果想反了）。

事实层写入机制（代码自动累积，LLM 不碰）

每次研报启动时，代码拉取数据后做两件事：① 组装第一轮消息注入研报 agent；② 按增量追加进 timeline 表——记录 since_ts(上次写入位置) 只写新内容，dedup_key(时间+标题哈希) 防重复。频率绑定研报启动（每天 3-4 次），两次之间的事件由下次 24h 全量拉取覆盖，信息不丢。

研报启动 → 代码拉取（快讯全量 + 日历 + 指标） ├─ 组装第一轮消息 → 注入研报 agent（预注入） └─ 增量追加 timeline 表（since_ts + dedup_key） 下次启动 → 读出近 7 天 timeline → 作为"时间线段"注入

LLM 写权限边界：研报 agent 对事实层只读（read_timeline），只写因果链层（submit_causal_links）；事实层是历史账本，因果链层是分析笔记，写权限严格分开。

因果链层（causal_links 表 · 分析笔记 · 复盘逐环验证）

因果链是有序节点链（从因到果的完整推导路径），只有研报 agent 能产生——代码提取不出"导致"关系。链上每个节点区分类型，可挂事实层引用，把推断锚在事实上：

{ "chain": [ {"node": "油价上涨", "kind": "事件", "timeline_id": "T-1024"}, {"node": "通胀预期上升", "kind": "推断"}, {"node": "美联储鹰派预期", "kind": "推断"}, {"node": "美债收益率上行", "kind": "市场反应", "timeline_id": "T-1031"}, {"node": "BTC 承压", "kind": "标的结论"} ], "confidence": 0.7, // 整条链的置信度 "evidence": ["..."], // 依据（可溯源） "report_id": "R-042" // 来源研报 }

复盘验证升级为"断点定位"：逐环节对照实际走势，标记断在哪一环（如"BTC 虽跌但美债环节未发生"→ 断点在"鹰派预期→美债"），错因精确到环节而非整条链；研报 agent 通过 L1 读近 7 天验证过的因果链记录自我纠错。 断点统计器（聚合"哪类环节经常断"供 L2 注入）按需加入——第一版只落库 + 逐环验证，跑起来发现 L1 纠错不足时再补。

5

复盘 agent 改动：从"只看自己"到"对照世界"

现状复盘只分析内部行为（成交/决策轮次/工具调用链），看不到外部环境。改动原则：不动现有逻辑，只加输入和工具。

现状盲区

复盘 agent 只能回答"我怎么做的"（这单追涨了），回答不了"为什么亏"（撞上非农冲击 vs 纯粹判断错）——行为和环境的因果分不开，复盘结论就浅。

改动清单（四个点）

① 简报输入扩展

复盘 briefing 增加三段：区间内研报判断史（时间/方向/置信度/依据）+ 事件时间线（时间/事件/来源）+ 实际走势（BTC/ETH 涨跌幅，代码算好不靠 LLM 猜）

② 新增工具（只读 + 修订，全部进统一审计）

只读工具（3 个）——复盘 agent 对照研报所需的"外部视角"数据：

get_report_judgments(period) — 读取指定时间区间内的研报判断史（时间/方向/置信度/核心依据/验证结果），复盘据此逐条对照"当时怎么看"

get_event_timeline(period) — 读取指定区间内的事件时间线（时间/事件/来源），帮复盘还原"当时外面发生了什么"

get_price_move(period) — 读取区间内的实际走势（BTC/ETH 涨跌幅、振幅），代码计算不靠 LLM 猜，是对照的"标准答案"

修订工具（1 个）——产出纠错动作：

submit_research_revision — 提交研报提示词修订（新提示词全文 + 修订理由 + 引用的错因统计），经五道护栏校验后版本化发布，研报 agent 下次自动加载（详见 5.4）

③ 输出扩展：研报对照小节

复盘报告新增"研报对照"表：研报 | 方向 | 置信度 | 实际走势 | 判定(对/错/偏对) + 偏差分析（错因分类 + 改进建议）

④ 偏差写回（闭环起点）

对照结论写回研报记录（验证结果 + 错因字段）——研报 agent 下次读判断史时能看到"我上次判得对不对"

错因分类（让校准有针对性）

信息不足

时间线缺关键事件，当时根本看不到

对策：补数据源 / 扩输入范围

解读错误

信息齐全但因果想反了（如放大美债、忽略 ETF）

对策：提示词修订（见 5.3）

时机偏差

方向对但时间点错（提前/滞后）

对策：调整 horizon 预期

5.3 三层纠错机制（纠错如何真正到达研报 agent）

难点：LLM 的"自我纠错"天然不可靠——告诉它"上次错了"，它下次会说"这次不一样"。只有改变它的输入或行为框架，纠错才生效。

L1 每次研报（短期）

判断史带验证结果 + 错因：研报 agent 每次输入近 7 天判断史，一睁眼就看到"我 3 天前看空错了，错因是低估 ETF 流入"

效果：提醒作用，基础但不强

L2 周期注入（中期）

代码每周统计错因分布，生成针对性指令注入研报系统提示词。例："近 7 天你的判断 3 次错在低估 ETF 资金面（08-01/03/05），给出高置信方向前先核对 ETF 净流入与稳定币市值"

效果：强。代码可控的输入变化，不靠 LLM 自觉

L3 结构性修正（长期）

某类错因连续高频（如连续 4 周"低估 ETF"），提示词提醒无效 → 结构性修改：输入结构调整（ETF 数据前置高亮）、horizon 调整、改研报提示词模板。由人（你）决定

效果：兜底。防失控

5.4 研报提示词版本化修订（复盘 agent 可改，带护栏）

边界：研报 agent 自己改自己 = 禁止（自我强化偏差）；复盘 agent 作为第三方、带证据、走版本化机制修订 = 允许。与策略修订（submit_strategy_revision）同一模式，机制现成。

护栏 ① 触发阈值

某错因近 7 天 ≥3 次且占比 ≥50% 才允许提交修订——防止每次复盘都动一下提示词

护栏 ② 频率上限

每 7 天最多 1 次研报提示词修订

护栏 ③ 范围限制

只能改"分析要求/权重提示"；输出 JSON 结构（direction/confidence schema）是代码强制，LLM 不可触碰

护栏 ④ 证据要求

提交必须带：新提示词全文 + 修订理由 + 引用的错因统计——没有证据不通过

护栏 ⑤ 人工兜底

版本历史可查可回滚（前端/数据库），人可随时撤销任何自动修订

落地方式

提示词存 research_prompt.md（运行时写回、不入库、同步 .example）；ResearchPromptStore 仿 StrategyStore 版本化 + 报告关联；研报 agent 下次运行自动加载最新版

复盘 agent 出偏差记录（验证结果+错因） ↓ 写回 reports 表 错因统计器聚合（每周） ↓ L2 注入 / 阈值校验 研报提示词修订（版本化发布，可回滚） ↓ 研报 agent 下次自动用新提示词 → 判断改变 ↓ 复盘再验证：错因分布下降 = 修订有效；不降 = 升级人工结构性修改（L3）
6

方向约束（代码级 gate）

研报结论对执行 agent 的约束不写在提示词里（提示词可被绕过），而是作为工具层的硬检查——与 RiskEngine 同级。

高置信看空

拒绝开多仓/加多仓调用（工具层拦截，返回拒绝原因）；已有仓位不受影响

高置信看多

拒绝开空仓/加空仓调用；已有仓位不受影响

中低置信度 / 中性

不拦截，研报结论仅作为上下文提示

实现位置：下单工具入口前新增 direction_gate(合约, 方向) 检查，读取当日最新研报的 direction+confidence，返回 allow(放行) / deny(拦截)。研报缺失时默认放行（不因系统故障阻塞交易）。硬约束的意义：方向错了最多错失行情，但执行 agent 永远不可能在逆势中开反向重仓。

安全底线（不可妥协）

1

研报/复盘 agent 无交易能力：只读工具 + 无密钥，结构上不可能触发交易

2

方向约束是代码 gate：工具层硬检查，LLM 不可绕过，与 RiskEngine 同级

3

统一审计：研报生成、复盘对照、gate 拦截、提示词修订全部进审计通道

4

护栏只防失控：研报/复盘工具调用均 ≤30 次（保险丝）+ 超时终止；token 不限量但日志统计，每月复盘成本

5

研报 agent 不自我修改提示词：修订只能来自复盘 agent（带证据、版本化）或人工；输出 schema 代码强制不可改

6

配置同步：新增研报/复盘配置段必须同步 config.example.yaml，否则 CI 挂

7

gate 默认放行：研报缺失/系统故障时不阻塞交易，宁可无约束不可锁死

8

实施计划（验证先行）

不做全量建设，先建最小闭环验证研报方向结论有没有判断力，再决定扩不扩。

阶段做什么验收标准
M1 研报骨架 数据源四类（金十 MCP + 律动 MCP + FRED + Polymarket）+ 研报 agent（10 工具 + 全量新闻预注入 + 结构化输出）+ 亚/欧/美盘调度触发（配置预留，第一期手动跑）+ reports/timeline/causal_links 表 + direction_gate（第二期）+ 复盘对照基础（判断史/时间线/实际走势读入，第二期） 四类源连通性实测通过；定时产出结构化研报落库；时间线自动累积；pytest 全绿
M2 验证期（核心） 复盘 agent 新增对照工具与"研报对照"小节 + 偏差/错因写回 + 错因统计器 + L2 注入 + submit_research_revision（五道护栏）+ 研报提示词版本化 两周准确率统计报告；错因分布可用；修订工具实测（构造错因超阈值 → 修订通过并版本化 → 研报下次加载新版）；pytest 全绿
M3 增强（按结果） 事件研报（5 星事件前 30 分钟）+ indicators 快照序列积累 + 新闻源扩展（RSS 英文源等） 按 M2 结论决定：通过则扩，不通过则停
动工顺序：M1 → M2（两周验证）→ 根据验证结果决定 M3。 整个方案的成败判据只有一个：研报方向结论的准确率是否显著高于随机（50%），以及纠错闭环能否让错因分布持续下降。
成本提示：放开 token 限制 + 全量新闻输入 + 每日复盘对照，月度 LLM 成本会明显上升。接受现状，M2 结束用日志统计评估性价比——方向准确率显著高于 50% 且错因下降，成本就是值得的投入；否则是省钱的依据。
